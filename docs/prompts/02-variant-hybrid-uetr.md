# Промпт 02 — Схема из двух баз: `Sklad_v1` (склад) + `Sklad_v1_HR` (кадры)

> **Часть проекта.** См. [README](../README.md) и [00-MAIN-PROMPT](../../docs/prompts/00-MAIN-PROMPT.md).
>
> **Эталон:** `Sh_29-06-25` — рабочая БД складского модуля.

## 1. НАЗНАЧЕНИЕ

Забрать из эталона **словарь и складскую логику**, а движения и деньги заменить
своим ядром: `Приход` / `Расход` / `Деньги`, связанные сквозным идентификатором
`UETR`. Три таблицы вместо восьми (`СкладПриход`, `СкладРасход`, `НакладнаяПриход`,
`НакладнаяРасход`, `КлиентДеньги`, `КлиентМеткаРасчет`, `ПРИХОД`, `РАСХОД`),
связь склад↔деньги — явная, а не «угадай по дате и клиенту».

**Кому подходит:** если приложение переписывается и данные эталона нужны как
источник понимания, но схему менять не страшно.

## 2. ЧТО БЕРЁМ ИЗ ЭТАЛОНА

| Эталон | В гибриде | Зачем |
|--------|-----------|-------|
| `Скдад` | `Warehouse` | Склад — сущность, без неё остаток не считается |
| `ОсновнаяЕдИзмерения` | `UnitMeasure` | м, кг, шт, пачка, бухта |
| `СвязиAlisЕдИмНоменклатура` | `PackUnitLink` | Коэффициент перевода и отдельная цена |
| `Матерьял`, `АтрибутыМатерьяла` | `Material`, `MaterialAttribute` | Комплектующие |
| `Номенклатура` | `Nomenclature` | Товар: название, материал, ед. изм., цена |
| `ХарактеристикаНоменклатуры` | `NomenclatureAttribute` | Расширения номенклатуры |
| `Клиент`, `Поставщик` | `Customer`, `Supplier` | Контрагенты (предел кредита сохранён) |

## 3. ЧТО НЕ БЕРЁМ И ПОЧЕМУ

| Эталон | Причина |
|--------|---------|
| `НакладнаяПриход`, `НакладнаяРасход` | Документом становится сам `UETR`; накладная — это `Date` + `Type` + контрагент |
| `СкладПриход`, `СкладРасход` | Заменяются на `Приход` / `Расход`: одна таблица вместо двух, поля без дублей |
| `КлиентДеньги`, `КлиентМеткаРасчет` | Деньги — таблица `Деньги`, долг считается запросом; «метка» заменена ревизией |
| `АудитМетка`, `РезультатАудита`, `АУДИД`, `ПРИХОД`, `РАСХОД` | Заменяются на `Ревизия` + `Расхождение` с вычисляемой дельтой |
| 9 процедур и 3 представления | Логика переносится в Dapper-запросы (перечень — в разделе 7) |

## 4. ЯДРО

### UETR — сквозной идентификатор документа

- `uniqueidentifier`, **не уникальный индекс**: один документ = несколько строк,
  все строки делят один `UETR`.
- Один `UETR` связывает `Приход` + `Расход` + `Деньги` — по нему собирается вся
  операция: что пришло, что ушло, какие деньги прошли.
- Выдаёт приложение при проведении документа (`NEWID()` или `NEWSEQUENTIALID()`).
- При переносе данных из эталона `UETR` детерминирован:
  `A0000000-…` — накладная прихода, `B0000000-…` — накладная расхода,
  `C0000000-…` — движение денег, `D0000000-…` — аудит-метка.

### `Приход` / `Расход`

Поля: `UETR`, `Date`, `Type`, `ПоставщикId`/`КлиентId`, `НоменклатураId`,
`СкладId`, `Quantity`, `Price`, `Sum`, `СотрудникGuid`, `Comment`.

Блок упаковки повторяет эталонную логику двух единиц, но **согласован**:
`CHECK` требует либо весь блок пустым, либо заполненным целиком. В эталоне этого
нет: `AliasЕдИм` заполнен, `колAliasЕдИм` — нули, коэффициенты — пустая таблица,
то есть механизм наполовину не работает.

### `Деньги`

`OperationType`: 1 получено, 2 выдано, 3 зарплата, 4 аванс.
`CounterpartyType`: 0 не задан, 1 клиент, 2 поставщик, 3 сотрудник.
`CounterpartyId` — полиморфная ссылка, `FOREIGN KEY` не создаётся; проверочный
запрос — в `database-schema.md`.

### `Ревизия` / `Расхождение`

`Ревизия.Code nvarchar(30)` — номер вида `REV-CLI-2026-0001`; `Type`, период,
`Status`, `DateCreated`.
`Расхождение` — «учёт против факта» по позиции; `Delta` — **вычисляемая** колонка
`ActualValue - AccountingValue`, поэтому не может разойтись с исходными числами.
В эталоне вместо этого `РезультатАудита.недостача` хранится вручную.

## 5. ТИПЫ

| Эталон | Гибрид | Зачем |
|--------|--------|-------|
| `float` | `decimal(18,3)` | Остатки и количества без ошибок округления |
| `smallmoney`, `money` | `decimal(18,2)` | Единый денежный тип |
| `nchar` | `nvarchar` | Пробелы в `nchar` ломают сравнения |
| строковые PK | `int IDENTITY` | Нормальные ключи и индексы |
| номенклатура «всё в одной таблице» | `Номенклатура` + `Материал` + `ЕдИзмерения` | Номенклатура — это изделие из материала, а не «материал с ценой» |

## 7. РАЗВЁРТЫВАНИЕ

```bash
# кадровая база — первой: основная ссылается на её Guid
cd db/sklad_v1_hr
sqlcmd -S localhost -E -f 65001 -b -i create-database.sql
sqlcmd -S localhost -E -f 65001 -b -i create-tables.sql
sqlcmd -S localhost -E -f 65001 -b -i create-indexes.sql
sqlcmd -S localhost -E -f 65001 -b -i insert-reference-data.sql

# основная база
cd ../sklad_v1
sqlcmd -S localhost -E -f 65001 -b -i create-database.sql
sqlcmd -S localhost -E -f 65001 -b -i create-tables.sql
sqlcmd -S localhost -E -f 65001 -b -i create-indexes.sql
sqlcmd -S localhost -E -f 65001 -b -i insert-reference-data.sql
sqlcmd -S localhost -E -f 65001 -b -i migrate-movements-from-Sh_29-06-25.sql
```

Порядок обязателен: `insert-reference-data.sql` заполняет справочники, по которым
миграция разрешает ссылки номенклатуры. `Id` справочников сохраняются из эталона
через `IDENTITY_INSERT` — иначе движения не найдут свою номенклатуру.

## 8. ЧТО ПРИХОДИТСЯ ДОДЕЛАТЬ В КОДЕ

| Задача | Что переносим из эталона |
|--------|------------------------|
| Остаток по складу | `ВналичиеНаСкладе` → `SUM(Приход.Quantity) - SUM(Расход.Quantity)` по `НоменклатураId, СкладId` |
| Долг клиента | `КлиентДолг` → `SUM(Деньги.Sum)` по `OperationType = 1` минус `OperationType = 2` |
| Последняя метка расчёта | `КлиентМеткаРасчетMax` → `MAX(Деньги.Date)` по клиенту |
| Отгрузка за период | `GetProdyktbyPeriod` → выборка `Расход` по `Date` |
| Отгрузка на дату | `GetProdyktbyDate` | |
| Выручка за период | `GetTotalSumByDate` → `SUM(Расход.Sum)` по периоду |
| Поставки за период | `GetПоставкиЗаПериод` | выборка `Приход` по `ПоставщикId, Date` |
| Итог аудита | `РезультатыАудита` → `SUM(Расхождение.Delta)` по `КодРевизии` |

## 9. ОГРАНИЧЕНИЯ

- ❌ НЕ делать индекс по `UETR` уникальным — в документе несколько строк.
- ❌ НЕ хранить `Delta` — только вычисляемая колонка.
- ❌ НЕ заводить упаковочные единицы без коэффициентов перевода.
- ❌ НЕ терять исходные `Id` справочников при переносе.
- ✅ Деньги привязывать к `UETR` документа, если операция связана со складом.
- ✅ Проверять `Деньги.CounterpartyId` в приложении (FK намеренно нет).
- ✅ Называть таблицы по-русски; английские имена остаются только у полей API-контракта.
- ✅ НЕ держать кадровые таблицы в основной базе — только в `Sklad_v1_HR`.
- ✅ НЕ менять `Guid` сотрудника после создания карточки.
- ✅ НЕ заполнять `Деньги.CounterpartyId` для сотрудника — только `СотрудникGuid`.
