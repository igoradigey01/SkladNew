# ERP-образцы: поиск номенклатуры, приход по накладной, быстрое создание

**Статус:** частично реализовано
**Дата:** 2026-11-12
**Контекст:** `Sklad-v4.1`, `SkladApi`, песочница `skladX01_v0`.
**Цель:** эталонные образцы в стиле Microsoft Dynamics NAV / Acumatica для трёх
сценариев ввода номенклатуры. SQL проверен по `db/sklad_v4_1/create-tables.sql`.

## 0. Важно: сверка с реальной схемой

Исходный текст-образец (сгенерированный ИИ) написан по «воображаемой» схеме.
Ниже — расхождения, из-за которых его SQL не выполнится:

| В исходном тексте | В реальной схеме `Sklad-v4.1` |
|---|---|
| `Номенклатура.БазовыйЕдИзмId` | `БазоваяЕдИзмId` |
| `Номенклатура.СоздалId` | колонки нет |
| «Категория = Товар» | `ТипId` int (1=Товар, 2=Услуга, 3=Материал); `КатегорияId` — отдельный справочник `КатегорияНоменклатуры` |
| `Приход.Type = 'ПриходПоНакладной'` | `Type` int (1=закупка у поставщика, 2=возврат от клиента, 3=выпуск, 4=перемещение, 5=инвентаризационная прибавка) |
| `Приход.СоздалId` | колонки нет; есть `СотрудникGuid uniqueidentifier NULL` |
| `ЗначениеХарактеристики.СоздалId` | колонки нет; есть `ДатаИзменения` (DEFAULT GETDATE()) |
| `Ревизия.Status = 'Проведена'` | `Status` int (1=создана, 2=в работе, 3=завершена, 4=отменена) |
| `Расхождение.СкладId` | колонки нет — склад в расхождении не хранится |

Следствие: «остатки по складу с учётом ревизии» по текущей схеме невозможны
(см. §5). Остаток по складам строится только из `Приход` и `Расход`.

## 1. Сценарий 1. Поиск и ввод номенклатуры в документ (Grid Lookup)

### Как это выглядит (NAV / Acumatica)

Пользователь не уходит из накладной. Он начинает печатать прямо в ячейке
«Товар» — под полем раскрывается таблица с живым фильтром.

```
┌ Товар ────────────────────────────────────────────────────────────┐
│ Болт М10                                                          │
├───────┬──────────────┬───────────────────────────┬────────┬────────┤
│ Код   │ Артикул      │ Название                  │ Ед.изм.│ Цена   │
├───────┼──────────────┼───────────────────────────┼────────┼────────┤
│ 00142 │ BLT-10-50    │ Болт М10х50 оцинкованный  │ шт.    │ 12,50  │
│ 00143 │ BLT-10-80    │ Болт М10х80 высокопрочный │ шт.    │ 18,00  │
│ 00201 │ BLT-10-60    │ Болт М10х60 нерж.         │ шт.    │ 24,00  │
├───────┴──────────────┴───────────────────────────┴────────┴────────┤
│ ➕ Создать новую номенклатуру «Болт М10…»                          │
└────────────────────────────────────────────────────────────────────┘
```

Правила поведения:
- автофокус на поле при открытии документа;
- фильтр с первого символа, `TOP 15`, только `Активен = 1`;
- `Enter` — выбрать первую строку, `↓/↑` — навигация, `Esc` — закрыть;
- пустой результат — подсказка «Ничего не найдено» + строка «Создать новую»;
- выбор подставляет в строку Id, название, ед. изм. и цену; фокус переходит
  на «Количество»;
- строка «Создать новую» открывает модалку из §4 (если сценарий включён).

### SQL быстрого поиска

Такой запрос заменит текущий `/candidates` (Ollama + векторы) для ввода
с клавиатуры: он быстрый и не зависит от доступности Ollama.

```sql
SELECT TOP (@limit)
    n.Id,
    n.Код,
    n.Артикул,
    n.Название,
    e.Сокращение            AS ЕдИзм,
    n.ЦенаЗакупочная,
    n.ЦенаПродажная
FROM dbo.Номенклатура AS n
JOIN dbo.ЕдИзмерения AS e ON e.Id = n.БазоваяЕдИзмId
WHERE n.Активен = 1
  AND (
        n.Код      LIKE @q + N'%'
     OR n.Артикул  LIKE N'%' + @q + N'%'
     OR n.Название LIKE N'%' + @q + N'%'
  )
ORDER BY n.Название;
```

Примечания:
- параметр `@q` передаётся через Dapper — инъекции нет;
- если нужен «строгий» поиск, символы `%` и `_` во вводе экранируются
  (`LIKE … ESCAPE '\'`);
- сортировка по `Название` — как в NAV по умолчанию; альтернатива —
  `ORDER BY CASE WHEN n.Код LIKE @q + '%' THEN 0 ELSE 1 END, n.Название`.

### Контракт будущего эндпоинта

```
GET /api/nomenclature/quick-search?q=Болт&limit=15
→ 200 [{ id, код, артикул, название, едизм, ценаЗакупочная, ценаПродажная }]
```

`/candidates` остаётся как «умный» поиск для голосового разбора, где опечатки
и синонимы важнее скорости.

## 2. Сценарий 2. Приход товара по накладной (Receipt)

### UX (Acumatica Receipt / NAV Item Journal)

```
Поставщик: ООО «МетизКомплект»      Склад: Основной        Дата: 2026-11-12
Вх. накладная №: 458 от 12.11.2026  UETR: a1b2c3d4-… (формируется при записи)

┌───────┬───────────────────────────┬─────────┬─────────┬───────────┐
│ Код   │ Название                  │ Кол-во  │ Цена    │ Сумма     │
├───────┼───────────────────────────┼─────────┼─────────┼───────────┤
│ 00142 │ Болт М10х50 оцинкованный  │ 500     │ 12,50   │ 6 250,00  │
│ 00145 │ Гайка М10                 │ 500     │  4,00   │ 2 000,00  │
└───────┴───────────────────────────┴─────────┴─────────┴───────────┘
Итого: 8 250,00
```

Правила:
- один документ = один `UETR`; отдельной таблицы-шапки у прихода нет —
  «шапка» (поставщик, склад, дата, комментарий) повторяется в каждой строке;
- `Sum` в БД хранится и проверяется CHECK-ом: `Quantity > 0`, `Price >= 0`,
  `Sum >= 0`; приложение считает `Sum = Quantity × Price`;
- `Comment` — место для «Накладная поставщика №458 от 12.11.2026»;
- `СотрудникGuid` заполняется, если известен сотрудник (nullable);
- сохранение — одной транзакцией: либо все строки, либо ни одной.

### SQL записи документа

```sql
BEGIN TRANSACTION;

DECLARE @uetr uniqueidentifier = NEWID();

INSERT INTO dbo.Приход
    (UETR, Date, Type, ПоставщикId, НоменклатураId, СкладId,
     Quantity, Price, Sum, Comment)
VALUES
    (@uetr, @date, 1, @поставщикId, @ном1, @складId,
     @qty1, @price1, @qty1 * @price1, @comment),
    (@uetr, @date, 1, @поставщикId, @ном2, @складId,
     @qty2, @price2, @qty2 * @price2, @comment);

COMMIT TRANSACTION;
```

Проверки перед вставкой (на сервере, не только в UI):
- все `НоменклатураId` существуют и `Активен = 1`;
- `СкладId` существует;
- `Quantity > 0`, `Price >= 0`;
- строк не меньше одной.

### Контракт будущего эндпоинта

```
POST /api/receipts
{
  "поставщикId": 14,
  "складId": 2,
  "дата": "2026-11-12",
  "комментарий": "Накладная поставщика №458 от 12.11.2026",
  "строки": [
    { "номенклатураId": 142, "количество": 500, "цена": 12.50 },
    { "номенклатураId": 145, "количество": 500, "цена": 4.00 }
  ]
}
→ 201 { "uetr": "…", "строк": 2, "сумма": 8250.00 }
```

Сервер сам генерирует `UETR` и `Sum` — клиент их не присылает.

## 3. Сценарий 3. Создание несуществующей позиции «на лету»

### UX модального окна (NAV Quick Create)

Открывается поверх документа, накладная не закрывается. После сохранения
новая позиция сразу подставляется в активную строку.

```
┌ Быстрое создание номенклатуры ────────────────────────── [×] ┐
│ Название *        [ Болт М12х60 нерж.                ]       │
│ Краткое           [ Болт М12х60                     ]       │
│ Код *             [ 00215                           ]       │
│ Артикул           [ BLT-12-60-SS                    ]       │
│ Группа            [ Крепёж / Болты            ▾ ]           │
│ Вид номенклатуры  [ Метизы                    ▾ ]           │
│ Тип               [ Товар (1)                 ▾ ]           │
│ Базовая ед. изм.* [ шт.                       ▾ ]           │
│ Цена закупочная   [ 24,00 ]   Цена продажная [ 39,00 ]      │
│ ── Характеристики вида «Метизы» ─────────────────────────── │
│ Резьба *          [ М12                       ▾ ] (список)   │
│ Длина, мм *       [ 60                          ] (число)    │
│ Материал          [ Нержавеющая сталь А2      ▾ ] (список)  │
│                                           [Отмена] [Сохранить и выбрать] │
└─────────────────────────────────────────────────────────────┘
```

Логика:
- «Название» префиллится из строки поиска;
- «Вид номенклатуры» определяет набор характеристик: строки берутся из
  `Характеристика` по `ВидНоменклатурыId`, где `Активен = 1`;
- тип значения задаёт `ТипЗначения` (`List` — селект из `СписокЗначений`,
  `Number` — число с `Минимум/Максимум`, `Text` — строка с
  `МаксимальнаяДлина`, `Date` — дата, `Bool` — флажок);
- `Обязательный = 1` — блокирует сохранение без значения;
- `Код` уникален (`UQ_Номенклатура_Код`) — при конфликте показываем ошибку,
  а не падаем.

### SQL транзакционного создания

```sql
BEGIN TRANSACTION;

DECLARE @newId int;

INSERT INTO dbo.Номенклатура
    (Код, Артикул, Название, КраткоеНазвание, ГруппаId, КатегорияId,
     ТипId, ВидНоменклатурыId, БазоваяЕдИзмId,
     ЦенаЗакупочная, ЦенаПродажная, Активен)
VALUES
    (@код, @артикул, @название, @краткое, @группаId, @категорияId,
     @типId, @видId, @едИзмId,
     @ценаЗакупочная, @ценаПродажная, 1);

SET @newId = SCOPE_IDENTITY();

-- Значения характеристик. JSON: [{"charId":10,"value":"М12"},
--                              {"charId":11,"value":"60"}]
INSERT INTO dbo.ЗначениеХарактеристики
    (НоменклатураId, ХарактеристикаId, Значение)
SELECT @newId, j.charId, j.value
FROM OPENJSON(@characteristicsJson)
WITH (
    charId int             '$.charId',
    value  nvarchar(500)   '$.value'
) AS j;

COMMIT TRANSACTION;
```

Проверки на сервере до COMMIT (иначе ROLLBACK):
- обязательные поля заполнены;
- `ТипId` ∈ {1, 2, 3} (есть CHECK в БД);
- `ВидНоменклатурыId` существует, если передан;
- для каждой характеристики: она принадлежит выбранному виду, `Обязательный`
  характеристики имеет значение, значение проходит по `ТипЗначения`
  (диапазон/длина/список).

`Guid` и `ДатаСоздания` заполняются DEFAULT-ами — клиенту их присылать не нужно.

### Удаление тестовой позиции после проверки

```sql
-- ЗначениеХарактеристики удаляется каскадом при удалении номенклатуры,
-- но явный DELETE безопаснее при ручной чистке тестов.
DELETE FROM dbo.ЗначениеХарактеристики WHERE НоменклатураId = @testId;
DELETE FROM dbo.Номенклатура           WHERE Id = @testId;
```

Тестовые позиции создавать с префиксом `ТЕСТ-` в `Код`, чтобы их было
легко найти:

```sql
SELECT Id, Код, Название FROM dbo.Номенклатура WHERE Код LIKE N'ТЕСТ-%';
```

## 4. Остатки: что можно и чего нельзя

Присланный `vw_StockBalance` не соответствует схеме: в `Расхождение` нет
`СкладId`, а `Ревизия.Status` — число, не строка. Поэтому остатки по складам
считаются только по движениям:

```sql
CREATE VIEW dbo.vw_ОстаткиПоСкладам
AS
SELECT
    s.Id    AS СкладId,
    s.Название AS Склад,
    n.Id    AS НоменклатураId,
    n.Код,
    n.Название,
    SUM(m.Qty) AS Остаток
FROM dbo.Склад AS s
JOIN (
        SELECT СкладId, НоменклатураId,  Quantity AS Qty FROM dbo.Приход
        UNION ALL
        SELECT СкладId, НоменклатураId, -Quantity AS Qty FROM dbo.Расход
     ) AS m ON m.СкладId = s.Id
JOIN dbo.Номенклатура AS n ON n.Id = m.НоменклатураId
GROUP BY s.Id, s.Название, n.Id, n.Код, n.Название
HAVING SUM(m.Qty) <> 0;
```

Вариант «показывать и нулевые остатки» — `CROSS JOIN` складов и номенклатуры
с `LEFT JOIN` движений (дороже на больших объёмах).

Корректировки ревизии в остаток не попадают, пока в `Расхождение` не появится
склад (или отдельная таблица расхождений по складам). Это отдельная задача
на изменение схемы, а не на UI.
