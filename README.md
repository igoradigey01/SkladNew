# Склад NEW — схемы БД

Новая схема хранилища: ядро на сквозном идентификаторе `UETR`, справочники
эталона по внутренним стандартам, кадры — в отдельной базе. Всё построено и
проверено на реальных данных рабочей базы `Sh_29-06-25` (эталон, 22 таблицы,
12 108 строк).

Версия 4 переделала систему характеристик по внешним стандартам:
тип значения атрибута, списки допустимых значений и наследование значений по
виду номенклатуры.

Версия 4.1 добавила слой взаиморасчётов с клиентом: сделки, накладные и
привязку платежей к сделке. Долг по сделке не хранится — он вычисляется.

## Что было найдено в эталоне по дороге

1. **Опечатки в именах влияют на скрипты.** `комeнтарий` в `КлиентМеткаРасчет` —
   с одной «м», `AliasЕдИзмТовар` — с `Изм`, а не `Им`. Русские имена содержат
   латинские и кириллические омоглифы, поэтому имена колонок берутся из
   `sys.columns`, а не набираются руками: опечатка даёт `Invalid column name`
   в самый неподходящий момент.
2. **Упаковочные количества не ведутся**: `колAliasЕдИм` равен нулю во всех
   строках движений, а таблица коэффициентов перевода пуста. Механизм второй
   единицы измерения есть, но не наполнен — поэтому в новых схемах упаковки нет.
3. **`АУДИД.количест` содержит 30 нулей**, а `РезультатАудита.недостача` бывает
   нулевой — ограничения `> 0` там невозможны, это учтено в CHECK.
4. **Один `UETR` = документ, а не строка.** Уникальный индекс по `UETR` сделать
   нельзя: в накладной несколько строк, все они делят один `UETR`.
5. **`FOREIGN KEY` между базами не существует.** Связь основной базы
   (`Sklad-v4` / `Sklad-v4.1`) с `Sklad_v1_HR` держится на `Guid`, плюс
   `CK_Деньги_Контрагент` запрещает заводить «свой» идентификатор сотрудника
   в основной базе.
6. **Колонка `КлиентДеньги.cуммаПринятыхДенег` в эталоне начинается с
   латинской `c`.** `cумма…` и `сумма…` — разные имена, опечатка даёт
   `Invalid column name`.

## Что осталось за рамками

- **Логика эталона** (9 процедур, 3 представления): остатки, долг клиента,
  отгрузки, поставки, итоги аудита. В варианте 1 они остаются в БД как есть,
  в рабочей схеме переносятся в запросы приложения — перечень в промте 02.
- **Backend и frontend**: .NET 8 + Dapper, API, Angular.
- **Наполнение новых справочников**: у 198 позиций номенклатуры не заполнены
  `Артикул`, `ЦенаЗакупочная`, `ЦенаОптовая`, складские параметры, `Фото` —
  в эталоне их не было.
- **Значения характеристик**: в эталоне пусто, заполняется при работе в системе.
- **Сервисы и API взаиморасчётов**: в v4.1 готова только БД. `DealService`,
  `InvoiceService`, `PaymentService`, Dapper-репозитории и контроллеры —
  следующая задача; контракт API описан в
  [`docs/reference/client-settlement.md`](../docs/reference/client-settlement.md).
- **Выпущенный продукт (Released Product)** из внешних стандартов: у нас одно
  юридическое лицо, роль «выпущенного продукта» играет `Номенклатура`.
  Если компаний станет несколько — понадобится отдельная таблица выпусков.
- **Тип значения хранится текстом** (`nvarchar`): одна колонка для всех типов,
  формат проверяют триггеры. Типизированные колонки (decimal / date / bit)
  дали бы проверку средствами `CHECK`, но усложнили бы запросы.
