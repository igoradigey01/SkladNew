# Схема БД `Sklad-v4` — версия 4

Версия 3 (`Sklad-v3`), но система характеристик переделана по внешним
стандартам: тип значения атрибута, списки допустимых значений и
наследование значений по виду номенклатуры.

Ядро (Приход / Расход / Деньги на общем `UETR`), ревизии и остальные
справочники перенесены из v3 без изменений.

Кадры по-прежнему в отдельной базе [`Sklad_v1_HR`](../sklad_v1_hr/database-schema.md),
связь — через `СотрудникGuid`.

## Что изменилось относительно `Sklad-v3`

| Таблица | Изменения |
|---------|-----------|
| `ТипЗначения` | **новая** — тип атрибута: Text, Number, Date, Bool, List |
| `Характеристика` | `ТипЗначенияId` (FK), `Минимум`, `Максимум`, `МаксимальнаяДлина`, `МинимальнаяДата`, `МаксимальнаяДата`, `ЗначениеПоУмолчанию`, `Описание`, `Активен`, `ДатаСоздания` |
| `СписокЗначений` | **новая** — допустимые значения для атрибутов типа `List` |
| `ЗначениеХарактеристики` | `ДатаИзменения` |
| `ВидНоменклатуры` | `Активен`, `ДатаСоздания` — вид можно отключить, не удаляя |

Добавлены: представление `vw_ЗначенияХарактеристик` (эффективное значение
атрибута) и три триггера (проверка значений по типу).

## Как устроена система характеристик

Логика атрибутов взята из внешних стандартов: атрибут заводится на
категорию и наследуется всеми позициями этой категории; значение по
умолчанию можно переопределить у конкретной позиции.

```
ВидНоменклатуры («Ткань», «ДСП», «саморезы» ...)
        │  основа для атрибутов — во внешних стандартах это Category
        ▼
Характеристика («Цвет», «Плотность», «Толщина» ...)
        ├── ТипЗначения ──► Text | Number | Date | Bool | List
        ├── Минимум / Максимум           (Number)
        ├── Минимальная / МаксимальнаяДата (Date)
        ├── МаксимальнаяДлина           (Text)
        ├── СписокЗначений              (List)
        └── ЗначениеПоУмолчанию         ← наследуется всеми позициями вида
        ▼
Номенклатура (карточка товара)
        ▼
ЗначениеХарактеристики ← переопределяет умолчание у конкретной позиции
```

| Понятие | Внешние стандарты | Наша схема |
|---------|-------------------|------------|
| Категория | Category | `ВидНоменклатуры` |
| Атрибут | Attribute | `Характеристика` |
| Тип атрибута | Attribute type | `ТипЗначения` |
| Допустимые значения | набор значений типа | `СписокЗначений` |
| Значение атрибута | поле в Released Product | `ЗначениеХарактеристики` |
| Выпущенный продукт | Released Product | `Номенклатура` |

**Отличие от внешних стандартов.** Во внешних стандартах значения атрибутов
хранятся прямо в карточке продукта, а не в отдельной таблице. У нас —
нормализованный вариант: `ЗначениеХарактеристики` отдельной строкой. Это
позволяет хранить историю и делать гибкие выборки («все ткани плотностью
120»), ценой одного JOIN.

**Released Product не переносился.** Во внешних стандартах продукт (Product) —
глобальное определение, а Released Product (выпущенный продукт) — его выпуск
в конкретную компанию с ценами, налогами и параметрами склада. У нас одно
юридическое лицо, поэтому роль «выпущенного продукта» играет сама
`Номенклатура`. Это точка роста: если появится несколько компаний,
понадобится отдельная таблица выпусков.

## Правила значений

Значение хранится текстом (`nvarchar`) — одна колонка для всех типов.
Формат и границы задаёт тип:

| Тип | Проверка | Пример |
|-----|----------|--------|
| `Text` | длина ≤ `МаксимальнаяДлина` | «100% хлопок» |
| `Number` | преобразуется в число, лежит в [`Минимум`, `Максимум`] | 120 |
| `Date` | преобразуется в дату, лежит в [`МинимальнаяДата`, `МаксимальнаяДата`] | 2026-10-20 |
| `Bool` | `0`/`1`/`true`/`false`/`да`/`нет` | да |
| `List` | значение есть в `СписокЗначений` | Белый |

### Почему триггеры, а не CHECK

Правила зависят от типа значения, а тип лежит в другой таблице, и список
допустимых значений — в третьей. В `CHECK`-ограничении подзапросы
запрещены: *«Subqueries are not allowed in this context. Only scalar
expressions are allowed.»* (`TRY_CONVERT` в `CHECK` разрешён, но тип всё
равно недоступен). Поэтому типозависимые правила вынесены в триггеры.

| Триггер | Событие | Что проверяет |
|---------|---------|---------------|
| `TR_Характеристика_Проверка` | INSERT / UPDATE `Характеристика` | `ЗначениеПоУмолчанию` по типу |
| `TR_ЗначениеХарактеристики_Проверка` | INSERT / UPDATE `ЗначениеХарактеристики` | значение позиции по типу |
| `TR_СписокЗначений_Проверка` | DELETE `СписокЗначений` | значение из списка уже используется — удалить нельзя |

Ограничения `CHECK` тоже есть, но только те, что не зависят от типа:
`Минимум ≤ Максимум`, `МинимальнаяДата ≤ МаксимальнаяДата`,
`МаксимальнаяДлина > 0`.

### Порядок заполнения типа List

`СписокЗначений` ссылается на `Характеристика`, поэтому список нельзя
заполнить раньше самой характеристики. Значение по умолчанию ставится
**третьим шагом** — когда список уже наполнен:

```sql
-- 1. характеристика
INSERT INTO dbo.Характеристика (ВидНоменклатурыId, ТипЗначенияId, Название)
VALUES (1, (SELECT Id FROM dbo.ТипЗначения WHERE Название = N'List'), N'Цвет');

-- 2. список значений
INSERT INTO dbo.СписокЗначений (ХарактеристикаId, Значение)
VALUES (1, N'Белый'), (1, N'Синий');

-- 3. значение по умолчанию
UPDATE dbo.Характеристика SET ЗначениеПоУмолчанию = N'Белый' WHERE Id = 1;
```

Пока список пуст, умолчание типа `List` не проверяется — иначе его негде
искать. Расхождения ловит проверка в `verify-data.sql` (раздел 5.1).

## Ключевые запросы

**Характеристики вида со всеми правилами** — то, что нужно форме
редактирования атрибута:

```sql
SELECT х.[Название],
       х.[Порядок],
       х.[Обязательный],
       тз.[Название] AS [ТипЗначения],
       х.[Минимум],
       х.[Максимум],
       х.[МаксимальнаяДлина],
       х.[ЗначениеПоУмолчанию]
FROM   dbo.[Характеристика] AS х
JOIN   dbo.[ТипЗначения] AS тз ON тз.[Id] = х.[ТипЗначенияId]
WHERE  х.[ВидНоменклатурыId] = @ВидНоменклатурыId
ORDER BY х.[Порядок];
```

**Допустимые значения для атрибута типа List** — источник выпадающего
списка в форме:

```sql
SELECT с.[Значение], с.[Порядок]
FROM   dbo.[СписокЗначений] AS с
WHERE  с.[ХарактеристикаId] = @ХарактеристикаId
ORDER BY с.[Порядок];
```

**Значения позиции** (как в задаче):

```sql
SELECT н.[Код],
       н.[Название] AS [Номенклатура],
       х.[Название] AS [Характеристика],
       зх.[Значение],
       тз.[Название] AS [ТипЗначения]
FROM   dbo.[Номенклатура] AS н
JOIN   dbo.[ЗначениеХарактеристики] AS зх ON зх.[НоменклатураId] = н.[Id]
JOIN   dbo.[Характеристика] AS х ON х.[Id] = зх.[ХарактеристикаId]
JOIN   dbo.[ТипЗначения] AS тз ON тз.[Id] = х.[ТипЗначенияId]
WHERE  н.[Код] = @Код
ORDER BY х.[Порядок];
```

**Эффективное значение** — переопределение позиции, иначе умолчание вида.
Берётся из представления, `Источник` показывает, откуда значение:

```sql
SELECT н.[Код],
       х.[Название] AS [Характеристика],
       COALESCE(зх.[Значение], х.[ЗначениеПоУмолчанию]) AS [Значение],
       CASE WHEN зх.[Id] IS NOT NULL THEN N'позиция' ELSE N'по умолчанию' END AS [Источник]
FROM   dbo.[Номенклатура] AS н
JOIN   dbo.[Характеристика] AS х ON х.[ВидНоменклатурыId] = н.[ВидНоменклатурыId]
LEFT JOIN dbo.[ЗначениеХарактеристики] AS зх ON зх.[НоменклатураId] = н.[Id]
                                          AND зх.[ХарактеристикаId] = х.[Id]
WHERE  н.[Код] = @Код
ORDER BY х.[Порядок];
```

То же самое, но целиком — `dbo.vw_ЗначенияХарактеристик`.

**Номенклатура с заполненными значениями** — фильтр «только те, у кого
все обязательные атрибуты заданы»:

```sql
SELECT н.[Код], н.[Название]
FROM   dbo.[Номенклатура] AS н
WHERE  н.[ВидНоменклатурыId] = @ВидНоменклатурыId
  AND  EXISTS (SELECT 1 FROM dbo.[Характеристика] AS х
               WHERE х.[ВидНоменклатурыId] = н.[ВидНоменклатурыId]
                 AND х.[Обязательный] = 1
                 AND NOT EXISTS (SELECT 1 FROM dbo.[ЗначениеХарактеристики] AS з
                                 WHERE з.[НоменклатураId] = н.[Id]
                                   AND з.[ХарактеристикаId] = х.[Id]));
```

Запросы по остаткам, долгу клиента и итогам ревизии — как в v3, ядро не
менялось.

### Вид «Ткань»

В эталоне вида «Ткань» нет (только ДСП, фанера, МДФ, ДВП, крепёж и
прочее), хотя проект — склад тканей. Вид добавлен в v4 вместе с набором
характеристик, чтобы новая система была видна в данных:

| Характеристика | Тип | Минимум | Максимум | По умолчанию |
|----------------|-----|---------|----------|--------------|
| Цвет | List | — | — | Белый |
| Плотность | Number | 10 | 500 | 100 |
| Ширина | Number | 10 | 1000 | 150 |
| Состав | Text | — | длина 200 | 100% хлопок |

Список цветов: Белый, Синий, Красный, Зелёный, Чёрный, Бежевый.

### Характеристики остальных видов

ДСП (Толщина 5–50, Цвет кромки, Материал), МДФ (Толщина 3–40, Покрытие),
ДВП (Толщина 2–30), фанера (Толщина 3–40, Сорт), кромка (Толщина 0,5–5,
Цвет), саморезы / болт / шурупы / гайка / шайба / гвозди / скоба
(Диаметр, Длина, Материал).

### Две пары одинаковых строк в расходе

В эталоне `НакладнаяРасход` 11 содержит две одинаковые строки (номенклатура
129, 3 шт по 250), а `НакладнаяРасход` 113 — две одинаковые строки
(номенклатура 128, 4,06 шт по 200). Это свойство исходных данных, а не
дефект переноса: в `Sklad-v3` те же строки, суммы сходятся с эталоном до
копейки. Проверка 7.1 в `verify-data.sql` их показывает.

## Особенности, о которых надо помнить

1. **Колонка `КлиентДеньги.cуммаПринятыхДенег` в эталоне начинается с
   латинской `c`.** Из-за омоглифа `cумма…` и `сумма…` — разные имена.
   Имена колонок берутся из `sys.columns`, а не набираются руками.
2. **Удаление вида номенклатуры блокируется**, если у его характеристик
   есть значения позиций: `FK_ЗначениеХарактеристики_Характеристика` —
   `ON DELETE NO ACTION`. Каскад `CASCADE` SQL Server принял бы, но он
   молча сносил бы значения позиций. Правильный путь — деактивировать вид
   (`Активен = 0`).
3. **Характеристику типа `List` нельзя создать сразу со значением по
   умолчанию**, если список ещё пуст: список ссылается на характеристику.
   Порядок: характеристика → список → умолчание.
4. **`CHECK`-ограничения не проверяют тип.** Вставка мусора отбивается
   триггером, но это срабатывает **после** проверки `UNIQUE`: если пара
   «позиция + характеристика» уже занята, сначала сработает `UNIQUE`.
   Для проверки типа существующего значения делайте `UPDATE`.
